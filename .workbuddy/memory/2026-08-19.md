## Netlify 构建失败根因与修复（重要可复用）
- 现象：连 Git 后首次构建在 `Install dependencies` 阶段失败，报错
  `Error: Digest method not supported` @ `scripts/prepublish.mjs:86` `nodeCrypto.createHash('sha-256')`。
- 根因 1：`.nvmrc` 写 `v16` → Netlify 用 Node 16；而 Node 16 不识别 `'sha-256'`（带连字符）这种非标准写法（Node 18+ 才容忍）。
- 根因 2：**Netlify 读取 Node 版本时 `.nvmrc` 优先级高于 `netlify.toml` 的 `[build.environment] NODE_VERSION`**；
  即使 netlify.toml 写了 18 也被 .nvmrc 的 16 覆盖。
- 修复：① 把 `.nvmrc` 的 `v16` 改成 `20`；② `prepublish.mjs:86` 的 `'sha-256'` 改成标准 `'sha256'`
  （跨版本兼容，真正 bug 修复）；③ netlify.toml 的 `NODE_VERSION` 同步改成 `20` 保持一致。
- 依赖链也要求高 Node（cheerio>=18.17、undici>=20.18），用 20 更稳。
- 用户本地用 Node v22 能 build 成功，故与本地一致即可。改完需重新 `git push`，Netlify 连 Git 会自动重构建。
- 上线前置：必须设 Netlify 环境变量 `SILICONFLOW_KEY`，否则函数运行时拿不到 key 报 server_missing_key。
- 3:31 PM 重新 trigger deploy 成功，1 function deployed，函数已能读到 `SILICONFLOW_KEY`；等待用户在浏览器 Network 验证 `/.netlify/functions/moderate` 调用。

## TwT 反馈系统改为受控 RPC（保留全部功能的安全加固）
- 直接给 anon 收 UPDATE/DELETE 会导致前端点赞/评论/删帖/改名失效（前端原走直连 PATCH/DELETE，报 42501）。
- 方案：表对 anon 仅 SELECT+INSERT；点赞/评论/删评论/删帖/改名改为 5 个 `SECURITY DEFINER` RPC，
  函数内 WHERE 严格约束（点赞按设备去重只 ±1、评论只追加、删帖校验 owner_id、改名只改自己行）。
- 关键修复：Postgres `jsonb - text` 对数组是把 text 当**索引**不是按值删 → 取消赞/删评论不能用，
  改用 `jsonb_array_elements` + `jsonb_agg` 过滤实现按值移除。
- 代码改动：`tw-feedback-schema-full.sql`（RPC + 权限）、`src/lib/tw-feedback-store.js`（加 `rpc()` 助手，
  online 改调 RPC，local 兜底实现对应方法）、`src/components/tw-feedback-modal/feedback-modal.jsx`
  （toggleLike/onSendComment/onDelete/onDeleteComment 改调 store.like/addComment/removeOwn/deleteComment）。
  `tw-feedback-schema.sql` 已标注废弃，统一用 full 版。更新日志加了 v2026.8.19 安全改进条目。
- 部署：① Supabase 跑 full SQL 一次（幂等）② `npm run build` ③ 保留 AI 审核需 Git push（含函数），

## 点赞失败根因（18:01 报"一点赞就失败"）
- 现象：前端 set_like RPC 一调用就失败。
- 根因：加固 SQL 把 `likers` 列写在 `create table if not exists public.feedback (... likers ...)` 里，
  而用户第 1 步跑 SQL 时 feedback 表已存在（旧表无 likers 列），`create table if not exists` 对已有表
  **不补列** → likers 实际缺失 → `set_like` 执行 `select ... likers` 报 "column likers does not exist" → 点赞失败。
- 原 schema 处理 owner_id 用的是 `alter table ... add column if not exists`（正确姿势）。已照此在
  tw-feedback-schema-full.sql 第 31 行附近补 `alter table if not exists public.feedback add column if not exists
  likers jsonb not null default '[]'::jsonb;`。
- 修复动作（用户侧）：Supabase SQL Editor 跑那条 ALTER（或重跑 full SQL 全文）即可，**无需重新部署前端**
  （前端 set_like 调用已在 5d3f218 上线）。评论/删帖/改名不受影响（comments、owner_id 列本就存在）。
- 教训：给"可能已存在的表"加列，必须用 `alter table add column if not exists`，不能塞进 create table if not exists。

## 严重越权漏洞修复（19:51 用户贴 PowerShell 删库脚本）
- 现象：一段 PowerShell 用 publishable(anon) key + `SELECT *` 读出所有 feedback 的 `owner_id`，
  再对每行调 `delete_own_feedback(p_id, p_owner=真实owner_id)` 把整张表删光。rename_username 同理（device_id 公开可读）。
- **根因（我之前设计的权限模型缺陷）**：删除/改名用"公开的 owner_id/device_id"做鉴权，而 anon 的
  `feedback read`/`usernames read` 策略是 `USING(true)`，任何人都能读到这些 ID → 鉴权形同虚设。
- **修复（能力令牌模型）**：
  - SQL：`feedback` 加 `owner_secret text`、`usernames` 加 `device_secret text`（均 `alter add column if not exists`）。
  - `delete_own_feedback(p_id, p_secret)` → `WHERE id=p_id AND owner_secret=p_secret`；
    `rename_username(p_device, p_name, p_secret)` → `WHERE device_id=p_device AND device_secret=p_secret`。
  - **关键**：`revoke select on ... from anon, authenticated` 后 `grant select (不含密钥列) ...`，
    禁止 anon 读取密钥列；RPC 以 SECURITY DEFINER 运行仍可读。另 `grant insert (含密钥列)`。
  - 前端 `tw-feedback-store.js` 新增 `getDeviceSecret()`（localStorage 随机值，每浏览器一个）；
    `online.add` 写 `owner_secret`、`setUsername` 写 `device_secret`；`removeOwn(id)` 与 `rename_username` 改带密钥。
  - modal `removeOwn(id, this.deviceId)` → `removeOwn(id)`（去掉不再需要的参数）。
  - changelog 新增 `sec` 标签（盾牌图标 + "安全"），更新日志加一条安全修复说明。
- **迁移权衡（务必告知用户）**：跑新 SQL 后，旧帖/旧昵称的密钥列为 NULL → 包括本人在内任何人都无法删除/改名
  （攻击者同样不能）。新发的帖、新设的昵称完全受保护且可正常删除/改名。这是安全优先的取舍。
- 改动文件：tw-feedback-schema-full.sql、src/lib/tw-feedback-store.js、src/components/tw-feedback-modal/feedback-modal.jsx、
  src/playground/changelog/changelog-data.js（仅加 sec 标签定义）。未碰 CSS/布局/编辑器，遵守纪律。
